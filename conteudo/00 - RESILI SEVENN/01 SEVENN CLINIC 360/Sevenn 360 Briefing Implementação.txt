## 3. ARQUITETURA DE DADOS & SEGURANÇA (SCHEMA)

**Regra de Ouro:** Toda tabela deve ter `clinic_id`. Toda query deve filtrar por `clinic_id`.
**Segurança:** Row Level Security (RLS) habilitado em todas as tabelas.

### Tabelas Principais (Schema V1)

1.  **`clinics`**
    * `id` (UUID, PK), `name`, `plan_tier` ('start', 'gold', 'black'), `status`, `created_at`.
2.  **`profiles`** (Extensão de auth.users)
    * `id` (FK auth.users), `clinic_id` (FK clinics), `role` ('owner', 'manager', 'staff'), `full_name`, `avatar_url`.
3.  **`leads`**
    * `id`, `clinic_id`, `name`, `phone`, `status` (active, archived), `sevenn_score` (0-100), `pipeline_stage_id`.
4.  **`pipeline_stages`**
    * `id`, `clinic_id`, `name` (Novo, Qualificado...), `order_index`, `color`.
5.  **`appointments`**
    * `id`, `clinic_id`, `lead_id`, `professional_id`, `service_id`, `start_time`, `end_time`, `status` (scheduled, confirmed, completed, no-show).
6.  **`services`**
    * `id`, `clinic_id`, `name`, `price`, `duration`, `material_cost` (CMV).
7.  **`professionals`**
    * `id`, `clinic_id`, `name`, `commission_rate` (Decimal), `color_hex`.
8.  **`financial_transactions`**
    * `id`, `clinic_id`, `amount`, `type` (income, expense), `category`, `status` (paid, pending), `appointment_id`.
9.  **`messages`**
    * `id`, `clinic_id`, `lead_id`, `content`, `sender` (user/lead/ai), `channel` (whatsapp/instagram).

## 9. CONTROLE DE ACESSOS INTERNOS (RBAC)

Este módulo blinda a aplicação, definindo **quem vê o quê**. A segurança é aplicada em duas camadas: Interface (UX) e Banco de Dados (Segurança Real).

### 9.1. Estrutura de Dados (Roles)
A tabela `profiles` (vinculada ao `auth.users`) possui a coluna obrigatória `role`:
* **Enum:** `'owner'`, `'manager'`, `'staff'`.
* **Padrão:** Novos convites de e-mail devem definir o role no momento da criação. O primeiro usuário (criador da conta) é sempre `'owner'`.

### 9.2. Regras de Interface (Frontend Logic)
O Frontend deve esconder visualmente elementos que o usuário não pode acessar.

* **Menu Lateral (Sidebar):**
    * **Financeiro:** Renderizar APENAS SE `role === 'owner' OR 'manager'`.
    * **Marketing / Configurações:** Renderizar APENAS SE `role === 'owner'`.
    * **Staff (Secretária):** Vê apenas *Agenda*, *Chat*, *Pacientes* e *Kanban*.
* **Botões de Ação (Critical Actions):**
    * **Botão `Deletar Lead`:** Renderizar APENAS SE `role === 'owner'`. (Evita que funcionário apague leads por erro ou má fé).
    * **Botão `Exportar Relatório Completo`:** Renderizar APENAS SE `role === 'owner'`.
* **Mascaramento de Dados:**
    * No "Super Modal" do Lead, o campo `Total Gasto (LTV)` deve aparecer como `R$ ****` se o usuário for `'staff'`.

### 9.3. Regras de Segurança (Backend / Supabase RLS)
A segurança real acontece no banco. Mesmo que um usuário "staff" tente chamar a API manualmente ou inspecionar o código, o banco deve rejeitar a leitura.

**Políticas de RLS (Row Level Security) Obrigatórias:**

1.  **Tabela `financial_transactions` (Financeiro):**
    * **Política:** `DENY ALL` para role `'staff'`.
    * **Regra SQL (Exemplo):**
        ```sql
        create policy "Staff cannot see finances"
        on financial_transactions
        for select
        using (
          (select role from profiles where id = auth.uid()) in ('owner', 'manager')
        );
        ```

2.  **Tabela `marketing_expenses` (Marketing):**
    * **Política:** Visível apenas para `'owner'`.

3.  **Tabela `leads` (Deleção):**
    * **Política:** `DELETE` permitido apenas para `'owner'`.
    * **Regra SQL (Exemplo):**
        ```sql
        create policy "Only Owner can delete leads"
        on leads
        for delete
        using (
          (select role from profiles where id = auth.uid()) = 'owner'
        );
        ```

**Resumo da Blindagem:**
Isso garante que, mesmo que a secretária seja "hacker" e tente chamar a API direto via Postman ou Console do Navegador, o Supabase retorna um erro de permissão (403 Forbidden), protegendo os dados financeiros da clínica.

3. Regras de Aplicação (Style Guide)
Para manter a consistência com a identidade "Resili Sevenn":
Botões de Ação (CTA):
Não usar cor sólida chapada. Usar Gradiente Linear Horizontal.
Regra CSS: bg-gradient-to-r from-[#59A52C] to-[#6fca3a] hover:opacity-90.
Isso dá o efeito "neon/vivo" que está na sua logo.
Sidebar (Menu Lateral):
No Light Mode: Fundo Verde Escuro (#060606 ou #0f1f0a) para dar contraste com o resto do painel branco. Isso ancora a marca.
Referência: Igual ao print que você mandou do painel financeiro, onde o menu é escuro e o conteúdo é claro. Fica muito elegante.
Gráficos e Dashboards:
Linha de Lucro/Vendas: Usar o #59A52C (Verde principal).
Despesas: Usar um Vermelho Suave (ex: #ef4444), nunca vermelho "sangue".
Neutros: Cinza para comparação com mês anterior.
