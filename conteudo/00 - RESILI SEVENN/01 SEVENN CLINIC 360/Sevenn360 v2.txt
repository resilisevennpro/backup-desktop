## 1. STACK TECNOLÓGICA & INFRAESTRUTURA

### 2.2 Componente `FeatureGate.tsx` (Implementação)

O componente wrapper `FeatureGate` controla a renderização baseada no plano:

* **Props:** `requiredPlan` (PlanTier: `start` | `gold` | `black`), `currentPlan` (default: `start`), `children`, `fallback`.
* **Lógica:** Hierarquia numérica `start=1, gold=2, black=3`. Se `planLevels[currentPlan] >= planLevels[requiredPlan]` → renderiza children. Caso contrário, exibe fallback ou UI de bloqueio padrão.
* **UI de Bloqueio Padrão:**
  * Área com `backdrop-blur-sm`, ícone Lock, texto "Funcionalidade Bloqueada", botão "Fazer Upgrade" que abre Dialog com opções de plano Gold (Agente IA + Instagram) e Black (Multi-WPP + Marketing).

## 3. ARQUITETURA DE DADOS & SEGURANÇA (SCHEMA)

**Regra de Ouro:** Toda tabela **DEVE** ter `clinic_id`. Toda query **DEVE** filtrar por `clinic_id`.
**Segurança:** Row Level Security (RLS) habilitado em todas as tabelas.

### 4.1 Arquitetura de Pipelines (Multi-Funil)
O sistema não opera mais com um único Kanban. A operação é dividida em 3 contextos distintos para evitar poluição visual e cognitiva.

1.  **Pipeline de Oportunidades (Vendas):**
    *   **Foco:** Conversão de novos leads em pacientes pagantes.
    *   **Estágios Típicos:** Novo Lead, Qualificado, Agendou Avaliação, Compareceu, Negociação, Venda Realizada.
2.  **Pipeline de Gestão de Pacientes (Ciclo de Vida):**
    *   **Foco:** Entrega do serviço e fidelização. O paciente entra aqui automaticamente após "Venda Realizada".
    *   **Estágios Típicos:** Em Tratamento, Aguardando Retorno, Finalizado, Alta.
    *   **Transição de Nomenclatura:** Reforçar o termo **"Procedimento"** ao invés de "Tratamento" para procedimentos estéticos pontuais.
3.  **Pipeline de Nutrição (Resgate):**
    *   **Foco:** Reaquecimento de base morta ou ociosa.
    *   **Estágios Típicos:** Lead Frio, Tentativa de Contato 1/2/3, Reaquecido.

### 4.2 Lógica de IDs Estruturados (Human-Readable)
* **Formato:** Série numérica simples (ex: `001`, `002`, `1042`).
* **Implementação:** UUID (`id`) como PK + coluna `custom_id` (Serial) gerada por Trigger/Sequence.
* **Busca:** Campo de busca global aceita nome e ID numérico.

### 4.3 Inteligência de Ciclo de Venda & SLA
* **SLA Dinâmico:** Badge na ficha do lead compara dias em aberto vs meta (`target_sales_cycle_days`).
* **Alerta Visual:** Badge Âmbar/Laranja se exceder SLA.
* **Cálculo Automático:** Ao fechar venda, sistema grava `closed_at` e `sales_cycle_days`.

### 4.4 Inteligência de Retorno (LTV) — Etapa 017
* **Gatilho:** Status `Concluído` em `appointments` → verifica periodicidade do serviço.
* **Ação:** Cria card no Pipeline Nutrição/Gestão com data de follow-up agendada para X meses.
* **Tag:** Lead recebe `Oportunidade Retorno`.
* **Status Atual:** A periodicidade de retorno por tag/procedimento está prevista no schema (`periodicidade_retorno_meses`) mas **ainda não implementada** no frontend.

## 6. MÓDULO FINANCEIRO & BI ESTRATÉGICO

O módulo Financeiro é o mais denso da aplicação, dividido em 4 sub-tabs acessíveis via URL (`/financeiro?tab=...`).

### 6.1 Visão Geral (Dashboard) — `FinanceDashboardTab.tsx`

#### 6.1.1 KPIs Principais (4 Cards)
| KPI | Fonte | Lógica |
|---|---|---|
| **Faturamento Bruto** | `metrics.totalRevenue` | Soma de `income` com `status = paid` no período |
| **Lucro Líquido** | `metrics.totalProfit` | `Faturamento - (Comissões + Materiais + CustosFixos)` |
| **Margem Líquida** | `metrics.profitMargin` | `(Lucro / Faturamento) × 100` |
| **Ticket Médio** | Calculado | `Faturamento / count(transactions)` |

* **Comparativo de Crescimento:** Query paralela ao período anterior (mesmo número de dias). Exibe `+X%` ou `-X%` no card de Faturamento Bruto.
* **Margem Status:** `>= meta` → "Ótima Performance" (emerald); `< meta - 5` → "Baixa Performance" (red); else → "Estável" (blue).

#### 6.1.2 Meta de Faturamento
* **Progress Bar:** `currentRevenue / revenueGoal × 100`, capped at 100%. Bar color `#59A52C`.
* **Fonte de Dados:** `clinics.meta_faturamento` via `fetchFinanceData`.

#### 6.1.3 Insight Margem de Contribuição
* Margem `< 0` → "Prejuízo Operacional" (vermelho), `< 15%` → "Margem Apertada" (âmbar), else → "Operação Saudável" (verde).

#### 6.1.4 Gráfico de Evolução de Vendas
* **Visão Diária:** `eachDayOfInterval(startOfMonth(now), now)` → Mapeia para revenue por dia. X-axis: '01', '02', etc.
* **Visão Mensal:** Agrupamento por mês (Jan, Fev...), disponível apenas se período selecionado >= 60 dias.

#### 6.1.5 Top 5 Pacientes
* Agrupamento de `income` por `patient` name → sort descending → `slice(0, 5)`.

#### 6.1.6 Lucratividade Real por Procedimento
* Agrupa por nome do procedimento, cruzando com `services` (whitelist). Procedimentos não oficiais → "Outros" (sem custo).
* **Toggle Gross/Net:** O usuário pode alternar entre visualização bruta e líquida.

#### 6.1.7 Planejamento Financeiro & Projeções (Credit Receivable Projection)

Este é o motor mais complexo do dashboard. Projeta os recebíveis de **crédito parcelado** pelos próximos 12 meses.

* **Lookback:** 24 meses de transações de crédito (`payment_method` ILIKE `%credit%` | `%crédito%` | `%credito%`).
* **Algoritmo de Distribuição de Parcelas:**
  1. Para cada transação de crédito: `parcelaLiquida = (amount × (1 - feePercent/100)) / installments`.
  2. Cada parcela é projetada para recebimento em `D+30 × parcela` → `addMonths(saleDate, p + 1)`.
  3. Parcelas caem em "buckets" mensais (0-11, sendo 0 = mês atual).
* **KPIs de Projeção:**
  * **Total Garantido (12 Meses):** Soma dos 12 buckets.
  * **Pico de Recebimento:** Mês com maior valor.
  * **Média Mensal:** Total / 12.
  * **Visão Trimestral:** Q1 (Jan-Mar), Q2 (Abr-Jun), Q3 (Jul-Set), Q4 (Out-Dez) baseado no mês real (`getMonth()`).
* **Charts:** BarChart (gradiente verde `#4ade80` → `#86efac`) + AreaChart (curva de recebimento).

#### 6.1.8 Sistema de Antecipação de Recebíveis

Modal wizard de 3 steps para registrar antecipações bancárias:

1. **Step 1 — Seleção de Mês:** Lista meses futuros com saldo > 0. Card clicável com nome do mês e valor disponível.
2. **Step 2 — Inputs:** Valor a antecipar (max = saldo do mês), Taxa da operação (% → calcula R$ automaticamente e vice-versa). Preview "Receberá Hoje".
3. **Step 3 — Confirmação:** Resumo (Mês, Valor Bruto, Taxa, Valor Líquido). Botão "Confirmar Antecipação".
* **Efeito no Projection:** Subtrai `valor_bruto_retirado` do bucket do mês de referência. Soma `valor_liquido_recebido` ao bucket do mês atual (index 0).
* **Persistência:** `antecipacoes_financeiras` table. `registerAnticipation()` no `useFinanceStore`.
* **Histórico:** Modal separado listando todas as antecipações registradas.

### 6.2 Inteligência Híbrida de Comissões — Engine (`useFinanceStore.fetchFinanceData`)

O cálculo de comissões é feito **linha-a-linha** (Row-Level Calculation) para cada transação de income.

#### 6.2.1 Pipeline de Cálculo (por transação)

```
A. Identificar Profissional → professionals.find(p => p.id === t.professional_id)
B. Calcular Taxa de Cartão:
   - payment_method === 'credito_parcelado' || 'credito' →
     - 1 parcela → config_taxas.credito_1x
     - 2-4 parcelas → config_taxas.credito_2x_4x
     - 5-8 parcelas → config_taxas.credito_5x_8x
     - 9+ parcelas → config_taxas.credito_9x_12x
   - Outros métodos → config_taxas[method]
   - transactionFeeVal = amount × (feePercent / 100)
C. Material Cost → materialMap.get(procedureName) || 0
D. Base de Cálculo:
   - baseDeCalculo = amount
   - IF professional.descontar_taxas → baseDeCalculo -= transactionFeeVal
   - IF professional.descontar_material → baseDeCalculo -= materialCostVal
   - IF baseDeCalculo < 0 → baseDeCalculo = 0
E. Comissão Final = baseDeCalculo × (professional.commission_percentage / 100)
```

#### 6.2.2 Lógica da "Fatia Laranja" (Custos Operacionais)

```
IF filtro de profissional/procedimento ativo:
  displayedFixedCosts = totalCardFees (apenas)
ELSE:
  displayedFixedCosts = totalCardFees + marketingInvested + totalOperatingCosts + totalTaxes
```

* **Impostos:** `totalRevenue × (clinics.imposto_aliquota / 100)` — zerado se filtro ativo.
* **Marketing:** `clinics.verba_marketing` — zerado se filtro ativo.
* **Operating Costs:** Todas as expenses `paid` EXCETO categorias 'Comissões', 'Taxas Financeiras', 'Impostos' (para evitar dupla contagem).

#### 6.2.3 Resultado Final

```
totalProfit = totalRevenue - (totalCommissions + totalMaterials + displayedFixedCosts)
profitMargin = (totalProfit / totalRevenue) × 100
```

## 10. CONTROLE DE ACESSOS INTERNOS (RBAC)

Este módulo blinda a aplicação, definindo **quem vê o quê**. A segurança é aplicada em duas camadas: Interface (UX) e Banco de Dados (Segurança Real).

### 10.1. Estrutura de Dados (Roles)
A tabela `profiles` (vinculada ao `auth.users`) possui a coluna obrigatória `role`:
* **Enum:** `'owner'`, `'manager'`, `'staff'`.
* **Padrão:** Novos convites de e-mail devem definir o role no momento da criação. O primeiro usuário (criador da conta) é sempre `'owner'`.


### 10.2. Regras de Interface (Frontend Logic)
O Frontend deve esconder visualmente elementos que o usuário não pode acessar.

* **Menu Lateral (Sidebar):**
    * **Financeiro:** Renderizar APENAS SE `role === 'owner' OR 'manager'`.
    * **Marketing / Configurações:** Renderizar APENAS SE `role === 'owner'`.
    * **Staff (Secretária):** Vê apenas *Agenda*, *Chat*, *Pacientes* e *Kanban*.
* **Botões de Ação (Critical Actions):**
    * **Botão `Deletar Lead`:** Renderizar APENAS SE `role === 'owner'`. (Evita que funcionário apague leads por erro ou má fé).
    * **Botão `Exportar Relatório Completo`:** Renderizar APENAS SE `role === 'owner'`.
* **Mascaramento de Dados:**
    * No "Super Modal" do Lead, o campo `Total Gasto (LTV)` deve aparecer como `R$ ****` se o usuário for `'staff'`.


### 10.3. Regras de Segurança (Backend / Supabase RLS)
A segurança real acontece no banco. Mesmo que um usuário "staff" tente chamar a API manualmente ou inspecionar o código, o banco deve rejeitar a leitura.

**Políticas de RLS (Row Level Security) Obrigatórias:**

1.  **Tabela `financial_transactions` (Financeiro):**
    * **Política:** `DENY ALL` para role `'staff'`.
    * **Regra SQL (Exemplo):**
        ```sql
        create policy "Staff cannot see finances"
        on financial_transactions
        for select
        using (
          (select role from profiles where id = auth.uid()) in ('owner', 'manager')
        );
        ```

2.  **Tabela `marketing_expenses` (Marketing):**
    * **Política:** Visível apenas para `'owner'`.

3.  **Tabela `leads` (Deleção):**
    * **Política:** `DELETE` permitido apenas para `'owner'`.
    * **Regra SQL (Exemplo):**
        ```sql
        create policy "Only Owner can delete leads"
        on leads
        for delete
        using (
          (select role from profiles where id = auth.uid()) = 'owner'
        );
        ```

**Resumo da Blindagem:**
Isso garante que, mesmo que a secretária seja "hacker" e tente chamar a API direto via Postman ou Console do Navegador, o Supabase retorna um erro de permissão (403 Forbidden), protegendo os dados financeiros da clínica.
